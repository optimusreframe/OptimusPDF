# Development Methodology (reusable)

> **Portability note**: this document is written to be copied as-is into any repository. Every concrete example (tool names, file paths, library names) is illustrative only — drawn from one project's history to show *why* a rule exists, never a dependency the rule needs to make sense elsewhere. If you strip all italicized examples, every rule should still stand on its own.

This document was generated by observing how work actually happened across multiple sessions on one project, not written speculatively. It does not exist elsewhere in that project's repo — it was assembled from execution reports, plan documents, and directly-verified session behavior. Do not add a rule here unless it was actually applied and produced a verifiable outcome (a fix, a caught defect, a closed decision). Update it the same way: only when a session reveals a new rule, a correction to an existing one, or a real incident worth keeping as an example.

---

## 1. Roles and model routing

Work is split across distinct roles, each potentially backed by a different model tier. The tiers themselves are a project/session choice (routing has changed over time even within the same project, by explicit user direction) — what's reusable is the *separation of roles*, not any specific model name:

- **Orchestrator** — holds the full session context, decomposes work, dispatches to other roles, synthesizes results, talks to the user.
- **Planner** — produces the implementation plan before code changes start. For significant or sensitive changes (see §3), the plan itself gets reviewed *before* implementation begins, not just the resulting diff.
- **Implementer** — writes the actual change, scoped to a closed, approved unit of work.
- **Auxiliary agents** (validation, exploration, research) — narrow, fast, disposable. Used for read-only discovery, running checks, or independent research that would pollute the orchestrator's context if done inline.
- **Adversarial reviewer** — a role, not a specific tool. It can be an external CLI agent or an internal subagent; what matters is that it is *independent* of the implementer (different context, ideally different model) and its job is explicitly to try to find what's wrong, not to confirm the work is fine. *Example: one project used an external CLI-based model for this role, then switched to an in-house subagent when the CLI tool stopped being the user's preference — the review discipline (plan-gate + diff-gate, described below) did not change, only the executor did.*
- **Validator** — runs the mechanical checks (typecheck, lint, tests, build) against exactly what will ship.
- **Verifier** — a fresh-context agent that confirms a "done" claim independently, with no memory of how the work happened. See §5.

**Rule: no self-certification.** The implementer never declares their own work done. A separate validator confirms the mechanical checks pass, and for anything claiming end-to-end correctness, a separate verifier (blind to the implementation session) confirms it independently.

## 2. Lifecycle of a unit of work

1. **Discovery** — read the actual current state before planning. Don't assume file locations, prior decisions, or "what's probably there" — check.
2. **Plan** — a closed plan for the specific unit of work. Ambiguities in a request get resolved explicitly (state the ambiguity, state the interpretation chosen, state why) rather than silently picked.
3. **Review gate (before implementing)** — required for changes that are *significant* (new data shape in a shared module, architectural change) or *sensitive* (security, data integrity, anything touching money/auth/encryption). Skipped for low-risk, additive, well-understood work. The reviewer's job here is to find what the plan gets wrong before any code is written — *one project's review gate caught, before implementation, that a proposed type change (`page: number | null`) would silently fail an existing filter (`Number.isInteger`), which is exactly the class of mistake a plan-gate exists to catch before it's expensive to fix.*
4. **Implement** — scoped to the approved plan. Don't expand scope mid-implementation without flagging it back.
5. **Validate** — mechanical checks against the exact change (see §5).
6. **Review gate (after implementing)** — diff review by the adversarial reviewer for the same category of change that needed a plan-gate. Real, reproduced findings get fixed; the review is not treated as passed until they are.
7. **Fresh-context verification** — for anything user-facing or claiming "this now works," a verifier with no session memory confirms it against the real artifact, not the implementer's description of it.
8. **Evidence capture and integration** — see §4 and §6.

## 3. What counts as "significant or sensitive" (triggers the review gate)

- Touches encryption, authentication, permissions, or anything where a silent failure has a security consequence.
- Introduces or changes a shared data shape/type that other code already depends on.
- Is a refactor of an engine/module already in production use (not a new, isolated addition).
- Has a legal, licensing, or compliance dimension (see §7 on independent cross-checks).

Additive, isolated, low-risk work (a new module that doesn't touch existing shared code, a copy/text change, a new test) does not need a pre-implementation gate — just the normal post-implementation validation.

## 4. Evidence discipline

"It works" is not evidence. What is:

- **Exact commands and their real output** — not "tests pass," but "47 files, 888 tests passed, 3 skipped" from an actual run, quoted, not remembered from an earlier point in the session.
- **Re-verify fresh when state may have changed.** A check that passed ten tool-calls ago is not proof the current state passes — re-run it against exactly what is about to ship, especially after any mechanical restructuring (splitting commits, rebasing, moving files).
- **Real artifacts over synthetic-only fixtures when the bug class is about structure or parsing.** A hand-built test fixture can miss the exact real-world condition that triggers a bug (encrypted object streams, unusual encodings, malformed-but-common inputs). When a bug is suspected to be structural, get or generate a *real* artifact of that kind before declaring it fixed. *Example: a project's encryption-detection bug looked fixed against synthetic test files, but the real user file (with restrictions stored inside a compressed, encrypted object stream) exposed a gap that no hand-built fixture reproduced — because the code path that failed only exists when a real encoder produces that structure.*
- **Independent validation of output, not just "no exception was thrown.”** For anything that produces a file/document, re-open and validate the output with a *different* tool than the one that produced it (e.g., a document generated by library A gets read back by library B, or its raw structure inspected directly) before calling it correct.
- **Cite counts you can verify, not counts you recall.** When resuming or auditing prior work, treat a memory or a prior session's notes as a claim to re-check, not a fact — confirm the number of passing tests, the commit SHA, the CI conclusion, etc. against the tool that is authoritative for it (test runner, `git`, CI API) before repeating the number.

## 5. Verification tiers

A layered model, cheapest-first, each tier catching what the previous one can't:

1. **Static** — typecheck + lint. Catches type errors and style/correctness lint rules. Cheap, run constantly.
2. **Unit/engine** — automated tests against the pure logic, no UI. Catches logic regressions.
3. **Build** — the actual production build succeeds and produces the expected output (right routes, right assets). Catches integration issues static checks miss.
4. **Live/end-to-end** — the feature exercised in a real runtime (browser, real process) with a real input artifact, output captured and independently inspected. This is the tier that catches "it compiles and the unit test mocks passed, but the real thing is subtly broken." Reserve it for user-facing changes or anything the lower tiers can't meaningfully exercise (rendering, file I/O against real formats, timing-sensitive UI).

Not every change needs tier 4. Use judgment: a pure-logic bugfix with full unit coverage doesn't need a browser pass; a new user-facing tool does.

## 6. Adversarial review protocol

- The reviewer's default posture is to try to break the plan/diff, not confirm it's fine.
- **A round-count cap (e.g., "at most 2 rounds of adversarial review") is a cap on the *cost of coordination*, not a license to ship a known, well-understood finding unfixed.** If a review round ends with a finding whose root cause and fix are already precisely identified, fix it and move on — don't spend a scarce review round re-confirming something you already know how to fix, but also don't declare victory and hide it because the round budget ran out.
- **Watch for review rounds fixing one thing and introducing another.** A second round exists partly to catch regressions the first round's fixes introduced — don't treat round 1's fixes as automatically safe.
- **For decisions with a non-technical dimension (legal, licensing, compliance, cost)**: run two independent evaluations (different models or different reviewers) *without either seeing the other's answer first*, then synthesize. Independent convergence on the same conclusion is much stronger signal than one reviewer confident in their own answer. If they diverge, that divergence itself is the finding to bring to the user — don't silently pick one.

## 7. Governance: branches, commits, and scope

- **Real code/config changes go through a branch → review → merge cycle**, not direct commits to the main branch — even when the same session already has the change validated and ready. This preserves a reviewable unit of history and a rollback point.
- **State deviations from this out loud, every time**, rather than letting them blend into normal history. A direct-to-main commit, a merge performed despite a known-red check, an emergency hotfix that skipped the plan-gate — all of these might be the right call, but they must be named as exceptions with the reasoning attached, not silently normalized. *One project's own audit surfaced exactly this: a documentation-only status file had been pushed directly to `main` outside the branch/PR pattern the rest of the session used — not caught until an explicit "flag any deviation" audit asked the question directly. That is the failure mode this rule exists to prevent: deviations are easy to miss unless something forces you to look.*
- **Merging with a known-failing check is sometimes correct, but never silent.** Before merging past a red check: (a) confirm via the CI history that the *same* check was already failing before this change (not caused by it), (b) confirm the failure is unrelated to what changed, (c) still tell the user it happened and why, and leave a real follow-up rather than letting a "known failure" become permanent background noise nobody owns.
- **Scope discipline.** Don't expand a task's blast radius beyond what was asked. Something noticed in passing that's worth fixing (dead code, a stale doc, a real bug outside the current task) becomes a flagged follow-up item, not an inline addition to the current change.
- **No invented state.** Don't report a pending item, a "done" status, or a methodology rule that wasn't actually observed/verified this session. If something can't be confirmed (an external dashboard toggle, a setting outside the accessible tooling), say so explicitly instead of assuming a default.

## 8. Parallelism vs. sequencing

Default to dispatching independent units of work in parallel — it's faster and each unit's context stays clean. Switch to strictly sequential (implement one, validate it, only then start the next) when:
- The user explicitly asks for it (often because they want to review/course-correct between units).
- The units are not actually independent (shared files, shared types, coupled behavior).
- The risk profile is high enough that catching a bad pattern in unit 1 should stop units 2-N from repeating it.

Both modes are legitimate; the choice should be explicit and stated, not a default nobody decided on.

## 9. Working-tree hygiene

- Before any operation that could discard uncommitted work, check status first, and prefer reversible moves (stash, rename, move-aside) over destructive ones.
- **When a working tree accumulates multiple logically-separate units of unfinished work with no commits yet, split them into separate, independently-valid commits before pushing** — don't force unrelated work into one giant commit just because it happened to land in the same session. A working technique: separate the files that belong to each unit (most are cleanly separable by path); for files that mix hunks from more than one unit, edit them down to just one unit's content, validate *exactly that resulting state* (not the whole original dirty tree) with the full check suite, commit, and only then bring back the remaining unit's hunks for its own commit. Re-verifying against the exact committed state (not "the tree as a whole, which happens to include this") is what catches a bad split before it ships.
- Validate what will actually be committed/shipped, not a superset of it. If other uncommitted or untracked work is sitting in the same working tree, isolate it (e.g., temporarily set it aside) before running the check suite that gates a commit — otherwise a pass or fail can be attributed to the wrong unit of work.

## 10. Session close discipline

- **Persist decisions and lessons somewhere durable**, not just in the conversation. A rule learned the hard way (a root-cause, a rejected simpler alternative and why, a technique that worked) is only reusable if it survives past the end of the session.
- **Flag out-of-scope findings as separate follow-ups** instead of fixing them inline (scope creep) or letting them silently disappear when the session ends.
- **Leave a current-state artifact** a future session (or a different person) can trust without re-deriving it from scratch: what's verified and working right now, what's blocked on a decision or resource outside your control, what's actionable without any blocker, and a recommendation for what to do next and why. Keep it honest about what wasn't checked, not just what was.
